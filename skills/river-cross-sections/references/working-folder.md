## What the working folder is

The working folder (WD) is the folder of one case, for example one river reach to be meshed. It contains the case configuration `rcs_config.json`, and every path in the configuration is relative to it. The skill scripts live in the skill folder, not in WD. They are always launched from WD:

```bash
cd <WD>
<python> <skill>/scripts/<script>.py [-c rcs_config.json] [arguments]
```

`<python>` is one of the two interpreters recorded in `rcs_config.json` (`python.geo` or `python.ogr`). Each script sheet in `docs/scripts/` says which one to use.

If the user's project already has its own layout, map it in `paths` and `inputs` of the configuration. Do not move the user's files.

## Folders, roles and allowed actions

| Folder | Role | Allowed | Forbidden |
|---|---|---|---|
| `layers/` | Data. The **original layers** of the user (breaklines, nodestrings, region points, DTM), the **derived layers** written by the skill (`<name><suffix>.gpkg`, e.g. `breaklines_50m.gpkg`), and their backups (`<name>_backup_<tag>.gpkg`). | Read everything. Create the derived layers once, as copies of the originals (`init_outputs.py`). Write a derived layer only through `write3.py` or `drop_regions.py`, which first make a tagged backup checked by SHA-256. | Writing, renaming or deleting an **original** layer or the DTM. Writing a layer that is open in QGIS (a `-wal` or `-shm` file next to it means it probably is): ask the user to close it first. Deleting backups. |
| `mesh/` | Meshes generated by the user in QGIS with BASEmesh (`.2dm`), and possibly the BASEMENT model files. | Read, to check the mesh (`check_mesh.py`) and its date compared with the layers. | Any write. If something must change, prepare the text or the instructions, and the user applies them. |
| `docs/` | Documentation of the case: the work log `workflow.md`, the case rules and exceptions `rules.md`, the sections table (CSV). | Create and update these files. Every action that changes the work (a layer written, a rule decided, an exception accepted) gets a dated entry in `workflow.md`. | Removing the user's documents. Logging trivial file operations. |
| `work/` | Intermediate files of the scripts: `graph.pkl`, centerline tables, `sec_in.json`, `bank_out.json`, `secs_new.json`, payloads, locked lines, SHA-256 of the originals. | Create, overwrite and delete freely. Nothing here is a deliverable. | Treating a file here as the truth: the layers on disk are. |
| `scripts/` | Not needed: the scripts are in the skill. Create it only when a case needs a script of its own, for example an adapted copy of a skill script. | Case-specific scripts, each with English comments and a sheet in `docs/scripts/`. | Modifying the skill scripts in place for one case. Copy the script into `WD/scripts/` and change the copy. |

The QGIS project file (`.qgz`/`.qgs`) and the BASEMENT model files (`model_*.json`) are never written, wherever they are.

## How a layer is written

1. **Before writing,** tell the user what will change and why, and wait for their confirmation. Deletions always need explicit consent.
2. **Check that the layer is closed.** If there is a `-wal` file next to it, ask the user to close the layer in QGIS (or save the edits and remove the layer from the project).
3. **Write it** with `write3.py <payload> <tag>`. The tag is the date plus a letter (`20261119c`). The script makes `<layer>_backup_<tag>.gpkg` of every layer it touches, checks the copy by SHA-256 and refuses to run if that backup already exists.
4. **Read it back from disk and check it** with code that did not produce it (`verify3.py`, `check_regions.py` and the others in [checks.md](checks.md)).
5. **Log the action** in `docs/workflow.md`: what changed, the backup tag and the result of the checks.

The originals are checked by SHA-256 at the start (`init_outputs.py` writes `work/sha_originals.txt`) and at the end of the work (`init_outputs.py --check`).

## How to find missing information

The configuration needs case knowledge: names of the boundary conditions, reaches, gauging stations, the region classes, the spacing, the near-node distance. When a value is missing:

1. **Look in the material already available,** in this order:
   - the case configuration;
   - `docs/` (rules, log, notes);
   - the layers themselves (nodestring names, region names and `mat_id`, field names, CRS, the DTM metadata);
   - the BASEMENT model files (read only);
   - the QGIS project (read only).
2. **If the value can be inferred,** propose it to the user with its source ("the nodestring `BC_upstream` looks like the inflow: confirm?").
3. **If it cannot,** ask the user. Ask only what changes the result, and group the questions.

Scripts never guess. When a configuration key is missing, they stop with a message that names the key. Find the value as above, write it in the configuration and run the script again.
